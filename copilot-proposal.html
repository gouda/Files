مقترح تقني للإدارة

اعتماد GitHub Copilot كمساعد برمجي لفريق تطوير البوابة الإلكترونية (SharePoint)

تسريع تنفيذ الـ CRs من داخل Visual Studio دون المساس بالبيانات الحساسة، مع خطة Subscription واضحة، ومعايير مشتركة للفريق، وضوابط Governance قابلة للتدقيق.

الملخص الوضع الحالي أين يسرّع العمل الـ Administration قياس الأثر الـ Plans خطوات التفعيل المعايير المشتركة حماية البيانات خطة التنفيذ المخاطر

الملخص التنفيذي

ما الذي نطلبه من الإدارة

  • الموافقة على Pilot Subscription بعدد 5 Seats (≈ $95 شهريًا ≈ 360 ريال) لمدة شهرين.

لماذا GitHub Copilot تحديدًا؟

  • مدمج في Visual Studio (2022 من Version 17.10، و2026) دون إضافات خارجية، ويعمل مع Repositories على Azure DevOps مباشرة؛ لا حاجة لنقل الكود إلى GitHub.
  • إدارة مركزية: Policies، Content Exclusion، Audit Log، وتحديد الـ Models المسموح بها من لوحة واحدة.
  • التزام تعاقدي بعدم استخدام بيانات عملاء Business/Enterprise لتدريب الـ Models، مع اتفاقية حماية بيانات (DPA).
  • معايير مشتركة تُحفظ كملفات داخل الـ Repository (Instructions / Skills / Agents) فتصل لكل عضو مع كل Branch تلقائيًا.
03

الجدول يربط كل نشاط يومي للفريق بالـ Feature المقابلة في Copilot، مع تقدير أولي للأثر. التقديرات مبنية على طبيعة العمل (كود متكرر وواجهات وIntegrations) وستُستبدل بأرقام مقاسة بعد مرحلة الـ Pilot.

الجزء المتكرر في كل CR: هنا العائد الأكبر

كل CR يعيد نفس العمل تقريبًا: نفس الـ Validations، نفس الـ Controls، نفس هيكل الكود، ونفس الـ Security Checks. هذا النوع من العمل هو أفضل ما يجيده Copilot بشرط أن يُكتب المعيار مرة واحدة كملف في الـ Repository (القسم 08) بدل أن يعيد كل مطوّر شرحه. الفكرة: Copilot لا "يخترع" الـ Control أو الـ Validation، بل يستخدم ما هو موجود بالطريقة الموحّدة.

العنصر المتكرركيف يُستخدم Copilot فيهما يُكتب مرة واحدة في الـ Repositoryالنتيجة
Form Validations الثابتة
الهوية، الجوال، البريد، التواريخ الهجرية…		عند كتابة أي Form يقترح Copilot تلقائيًا الـ Validators الموحّدة من مكتبة الفريق (Server + Client) بدل كتابة Regex جديد في كل CRملف Instructions يقول: "لا تكتب validation جديدًا؛ استخدم Portal.Validation.*" + Skill يشرح كل validator ومتى يُستخدمتوحيد الرسائل والسلوك، وإزالة سبب شائع لأخطاء QA

تنبيه مهم للإدارة: الـ Security Agent داخل Copilot يقلّل ما يصل للمراجعة يدويًا، لكنه لا يستبدل الـ Security Gate في الـ CI/CD. التوصية أن تبقى الفحوصات الملزمة (Static analysis / Secret scanning / OWASP dependency check) خطوة إلزامية في Pipeline الـ Test، وأن يكون Copilot أداة "تصحيح مبكر" قبل الوصول إليها.

ما الذي لن يحلّه Copilot

  • قرارات الأعمال والموافقات: تبقى مع فريق الـ Business وفريق الـ QA.
  • خصوصيات SharePoint في بيئة الجهة (Farm Solutions، إعدادات الخادم، صلاحيات AD): يقترح، لكن الخبرة البشرية هي الحكم.
  • لن يصل إلى البيانات الفعلية أو الـ Production أبدًا؛ يعمل على الكود فقط.

قاعدة ذهبية للفريق

Copilot يقترح والمطوّر يقرر. كل كود مولّد يخضع لنفس الـ Review Flow الحالي (PR → Test → QA → UAT) دون أي اختصار. الأداة ترفع سرعة الكتابة والفهم، أما ضمان الجودة فيبقى في مسار الفريق كما هو.

04

الأثر على مهام الـ SharePoint Administration

إلى جانب تنفيذ الـ CRs، يتحمّل الفريق مهام تشغيلية دورية على الـ Farm: الترقية لنسخة أحدث، تنزيل الـ Security Updates، تثبيت الـ Workflow Manager، ضبط الـ Search Service Application، وإدارة الـ Timer Jobs. Copilot لا يتصل بالخوادم ولا ينفّذ شيئًا عليها، لكنه يسرّع الجزء الذي يستهلك معظم الوقت في هذه المهام: كتابة الـ PowerShell Scripts، قراءة الـ Logs، وبناء الـ Runbooks والـ Checklists.

  • patch-runbook (Prompt) — يولّد Runbook كامل لأي Update: ترتيب الـ Servers، أوامر التحقق، وخطة الـ Rollback.
  • custom-timer-job — قالب Timer Job بمعايير الفريق (Logging، Error Handling، Schedule، Feature Receiver).

الأداة المناسبة

Copilot يعمل على ملفات .ps1 داخل Visual Studio، لكن تجربة الـ PowerShell أفضل في VS Code مع نفس الـ Seat ونفس الـ Policies (الـ Content Exclusion يُطبّق على الاثنين). يُنصح أن يستخدم من يتولى مهام الـ Administration VS Code لهذا الجزء تحديدًا.

ضوابط خاصة بهذا الجزء: مهام الـ Administration تلمس معلومات أكثر حساسية من الكود: الـ Farm Topology، أسماء الـ Servers، الـ Service Accounts، الـ Passphrase، وإعدادات الـ Certificates. لا يُلصق أي من ذلك في الـ Chat؛ تُكتب الـ Scripts بـ Placeholders وتُعبَّأ القيم الفعلية على الـ Server وقت التنفيذ. كذلك قد يقترح Copilot بثقة Cmdlets غير موجودة في نسختنا أو تختلف بين 2016 و2019 و Subscription Edition؛ لذلك يُثبَّت الـ Version في ملف الـ Instructions، ويُتحقق من كل Cmdlet بـ Get-Command على الـ Test Farm قبل اعتماده. أي Script ناتج يمر بمسار الـ Change Management المعتاد ولا يُنفَّذ على الـ Production مباشرة.

06

لماذا Business وليس Enterprise؟

  • الـ Features الإضافية في Enterprise (الـ Code Indexing على GitHub.com، الـ Chat داخل الموقع) تفترض أن الـ Repositories على GitHub؛ الـ Repositories لدينا على Azure DevOps.
  • Business يوفر كل ما نحتاجه للحوكمة: الـ Policies، الـ Content Exclusion، الـ Audit Log، والالتزام بعدم التدريب.
  • فرق التكلفة يتيح مضاعفة عدد الـ Seats بنفس الميزانية.

07

خطوات الـ Subscription والتفعيل

الترتيب مهم: الشبكة والـ Policies أولًا، ثم الـ Seats، ثم المطوّرون. بهذا الترتيب لا يفتح أي مطوّر الأداة قبل أن تكون الضوابط قائمة.

أ. على مستوى الجهة (مرة واحدة)

  1. إنشاء Organization على GitHub باسم الجهة وبريد رسمي، وتفعيل الـ 2FA إلزاميًا لجميع الأعضاء.
  2. تفعيل Copilot Business من إعدادات الـ Organization وشراء عدد الـ Seats المعتمد (Monthly Billing قابلة للإلغاء).
  3. ضبط الـ Policies قبل تعيين أي Seat: إيقاف الـ Suggestions المطابقة للـ Public Code، تحديد الـ Models المسموح بها، منع الـ MCP Servers غير المعتمدة، وإيقاف الـ Web Search من الـ Chat.
  4. إدخال قواعد Content Exclusion (القسم 09) على مستوى الـ Organization.
  5. وضع Spending Limit لرصيد AI Credits الإضافي = صفر خلال التجربة.
  6. تنسيق مع فريق الـ Network لفتح Domains GitHub Copilot المنشورة في وثائق GitHub (Network settings) لأجهزة الفريق فقط، مع دعم الـ Proxy إن وُجد.

ب. على مستوى كل مطوّر

  1. إنشاء حساب GitHub بالبريد الرسمي والانضمام للـ Organization (لا حسابات شخصية).
  2. يعيّن الـ Admin Seat للمطوّر.
  3. في Visual Studio: تسجيل الدخول بحساب GitHub من File → Account Settings؛ Copilot مضمّن في VS 2022 (17.10+) و VS 2026 دون تثبيت.
  4. فتح الـ Solution من Repository على Azure DevOps كالمعتاد؛ ستُطبّق قواعد الـ Content Exclusion تلقائيًا لأن الـ IDE يرسل عنوان الـ Repository للتحقق من الـ Policy.
  5. التحقق: فتح ملف داخل الـ Content Exclusion (مثل web.config) والتأكد من ظهور أيقونة التعطيل وعدم ظهور اقتراحات.
  6. توقيع الـ Acceptable Use Policy وحضور Onboarding Session (ساعتان).
نقطة تحتاج قرارًا: خطة Business تعتمد على حسابات GitHub عادية داخل الـ Organization (مع إلزام 2FA). ربط الحسابات بـ SSO/Entra ID أو حسابات مُدارة (EMU) يتطلب GitHub Enterprise. إذا اشترطت Policy الجهة الربط الكامل بالـ SSO / Entra ID، فسيغيّر ذلك الخطة والتكلفة، ويستحسن حسمه مع الـ InfoSec مبكرًا.
08

كيف تصبح المعايير والـ Skills مشتركة بين الفريق؟

الميزة الأهم للفريق ليست في الـ Suggestions الذكية بل في توحيد طريقة العمل. Copilot يقرأ ملفات Instructions من داخل الـ Repository؛ وبما أن كل مطوّر يأخذ Branch من نفس الـ Repository، فإن هذه الملفات تصل للجميع تلقائيًا وتُراجع وتُحدّث عبر PR مثل أي كود.

النوعالموقع في الـ Repositoryالغرض
Custom Instructions
قواعد دائمة		.github/copilot-instructions.mdتُطبّق على كل تفاعل: لغة الـ Comments، الـ Naming Convention، استخدام الـ Common Controls والـ Validators الجاهزة بدل إعادة كتابتها، حظر تخزين الـ Secrets في الكود، رقم الـ CR في كل Commit.
Scoped Instructions
قواعد حسب نوع الملف		.github/instructions/*.instructions.mdقواعد لملفات JavaScript فقط أو لطبقة الـ Integration Mapping فقط (مثال: كل استدعاء يمر عبر الـ Common DLL ولا يستدعي أي API خارجي مباشرة).
Agent Skills
Skills لمهام محددة		.github/skills/<name>/SKILL.mdيُحمَّل عند الحاجة فقط: خطوات تحويل HTML إلى User Control، قالب الـ Mapping مع الـ Common DLL، Checklist قبل الـ PR.
Custom Agents
شخصيات بأدوات محددة		.github/agents/*.agent.mdمثل Agent باسم "Merge Reviewer" الذي يفحص الـ Diff مقابل قائمة الفريق فقط، أو Agent باسم "SharePoint Assistant" المقيّد بالأدوات الآمنة.
Prompt Files
أوامر جاهزة		.github/prompts/*.prompt.mdأوامر متكررة بضغطة واحدة: "ولّد الـ Release Notes لهذا الـ CR"، "اكتب اختبارات لهذه الدالة".

من "Copilot Memories" الفردية إلى معايير الفريق

بعض أعضاء الفريق يستخدمون حاليًا ميزة Copilot Memories في Visual Studio: أثناء الـ Chat يلتقط Copilot تفضيلات المطوّر ("استخدم الـ Repository Pattern"، "لا تكتب inline styles") ويطلب الإذن لحفظها. المهم إدراكه أن هذه الميزة لا تخزّن شيئًا سحريًا؛ هي تكتب القاعدة في أحد ملفين:

وجهة الحفظالنطاقالأثر على الفريق
%USERPROFILE%\copilot-instructions.mdشخصي — جهاز المطوّر فقطلا يُشارك يختفي مع تغيير الجهاز، لا يراه الزملاء، ولا يخضع لمراجعة
.github/copilot-instructions.md داخل الـ Repositoryالـ Repository — كل من يأخذ Branch منهمشترك ومُراجَع يصل للجميع مع كل Branch، ويُحدَّث عبر PR مثل الكود

الخطوة العملية: جمع القواعد المتراكمة في الملفات الشخصية لدى أعضاء الفريق، تنقيحها، ونقلها إلى ملف الـ Repository في أول أسبوع من التجربة. بعدها يبقى الملف الشخصي للتفضيلات الفردية فقط (مثل أسلوب التعليقات)، وكل ما يخص "كيف يبني الفريق البوابة" يعيش في الـ Repository. عند ظهور Memory جديدة لاحقًا يختار المطوّر "Repository" بدل "Personal" إن كانت قاعدة فريق.

تمييز مهم: توجد أيضًا خدمة باسم مشابه، Copilot Memory المستضافة على GitHub (تخزّن حقائق عن الـ Repository على خوادم GitHub وتنتهي صلاحيتها بعد 28 يومًا، وتُستخدم مع الـ Cloud Agent والـ Code Review). هذه غير مطلوبة لخطتنا لأن الـ Repositories لدينا على Azure DevOps، ويُنصح بإبقائها معطّلة من Policies الـ Organization حتى لا يخرج أي سياق إضافي عن الأداة.

Skills مقترحة للبدء بها

  • cr-scaffold — يولّد هيكل CR كامل (Page، Code-behind، Service، Mapping، Test) بالأسماء والمجلدات المعتمدة.
  • html-to-aspx-usercontrol — خطوات نقل Markup فريق الـ Front-end إلى .aspx/.ascx مع استبدال الأجزاء المتكررة بالـ Controls الجاهزة.
  • common-controls-catalog — فهرس الـ User Controls الموحّدة: الاسم، الخصائص، مثال، ومتى يُستخدم.
  • form-validation-standard — الـ Validators المعتمدة (Server + Client) ورسائلها، وقاعدة "لا validation جديد".
  • integration-dll-mapping — كيف يُستدعى الـ Common DLL لكل Integration (نفاذ وغيره)، نمط الـ Mapping، ومعالجة الاستجابة والأخطاء.
  • cr-branch-workflow — تسمية الـ Branch برقم الـ CR، ترتيب الـ Merge Test → QA → UAT → Production، وقالب وصف الـ PR.
  • security-reviewer (Agent) — قائمة الـ Security Checks الموحّدة كبنود يفحصها الـ Agent على الـ Diff قبل الـ PR.

آلية الـ Governance على المعايير

  • تُحفظ كل ملفات الـ Instructions في مجلد .github/ داخل Repository البوابة، وتُحمى بـ Branch Policy تتطلب مراجعًا واحدًا على الأقل.
  • Skill جديدة = PR جديد، يراجعه قائد الفريق. هكذا لا يغيّر أحد سلوك الأداة للجميع دون علم.
  • للـ Repositories المتعددة: Repository مركزي team-copilot-standards يُنسخ منه المجلد عبر خطوة في الـ CI/CD أو Git submodule.
  • مراجعة ربع سنوية للـ Skills لحذف ما لم يعد يُستخدم.

# copilot-instructions.md (excerpt)
- Target: SharePoint on-prem portal, ASP.NET WebForms (.aspx / .ascx / master pages)
  with C# code-behind on .NET Framework 4.x; jQuery for client-side.
- Structure per CR: Pages//.aspx + .aspx.cs, Services/Service.cs,
  Mapping/Mapper.cs, Tests/Tests.cs. Do not deviate.
- Reuse first: check Controls/ (user controls) and Portal.Validation.* before
  writing any new markup or validation. Never write a new Regex validator.
- Integrations: never call external systems directly. Always go through the
  Integration team's Common DLL (Portal.Integration.*); write only the mapping
  between page models and DLL models, and handle IntegrationResult uniformly.
- Security (every CR): check SPContext user permissions before any data access,
  validate and encode all input/output, keep AntiForgery on postbacks, never
  expose exception details to the UI, never log personal data.
- Design: use only the approved CSS classes / design tokens; no inline styles,
  no raw hex colors; all UI strings Arabic and RTL-safe.
- Dispose SPSite/SPWeb objects you create; never dispose SPContext.Current objects.
- Never hard-code secrets, connection strings or certificates; read from web.config.
- Every commit message starts with the CR number, e.g. "CR-1042: ...".
- Branch flow: CR-branch -> Test -> QA -> UAT -> Production. Never suggest skipping a stage.
متطلب Version: الـ Custom Instructions مدعومة في VS 2022 (17.14+)، أما Agent Skills والـ Custom Agents فتحتاج Visual Studio 2026 (18.4+). ينبغي التأكد من Version الـ VS المستخدم لدى الفريق قبل الاعتماد على الـ Skills.
09

حماية المستندات والبيانات الحساسة

الهدف: استخدام الأداة على الكود فقط، ومنع وصولها إلى وثائق المتطلبات (BRD)، والـ Secrets، وبيانات المواطنين. نعتمد ثلاث طبقات مستقلة بحيث لا يكفي فشل طبقة واحدة لحدوث تسريب.

الطبقة 1تعاقدية
الخطة الصحيحة تمنع التدريب أصلًا. في Copilot Business لا تُستخدم المدخلات أو المخرجات أو مقتطفات الكود لتدريب الـ Models، ولا يظهر خيار "السماح بالتدريب" لأن البيانات محمية باتفاقية حماية بيانات. تمر الطلبات عبر Proxy لدى GitHub على Azure مع فحص مسبق، ولا يُحتفظ بالمقتطفات لأغراض التدريب.
الطبقة 2تقنية مركزية
Content Exclusion على مستوى الـ Organization. يحدد الـ Admin ملفات ومسارات لا يقرؤها Copilot إطلاقًا: لا اقتراحات داخلها، ولا تُستخدم كسياق لملفات أخرى، ولا تُقرأ في الـ Chat. القواعد تُطبّق على Repositories على Azure DevOps بذكر عنوان الـ Repository، وعلى أي ملف خارج Git بنمط *:، وكل تغيير في القواعد يُسجّل في الـ Audit Log. أمثلة القواعد أدناه.
الطبقة 3سلوكية وتنظيمية
الـ Acceptable Use Policy وفصل المستندات عن الكود. وثائق BRD تبقى على Jira/SharePoint ولا تُنسخ إلى الـ Repository أو إلى نافذة الـ Chat؛ الـ Secrets تبقى في ملفات الـ Config داخل الـ Content Exclusion أو في Key Vault؛ وأي stack trace يُنظَّف من بيانات المستخدمين قبل لصقه. الفريق يوقّع الـ Policy، ويُفعّل Secret Scanning في Azure DevOps كشبكة أمان إضافية.

قواعد الـ Content Exclusion المقترحة (على مستوى الـ Organization)

# Any repo (Git or not): secrets & config
"*":
  - "**/web.config"
  - "**/appsettings*.json"
  - "**/*.pfx"
  - "**/*.pem"
  - "**/*.cer"
  - "**/secrets/**"
  - "**/*.env"

# Portal repo on Azure DevOps
"https://dev.azure.com/<org>/<project>/_git/portal":
  - "/docs/**"          # BRDs, SRS, meeting notes
  - "/integrations/nafath/config/**"
  - "/data/**"          # sample exports
  - "**/*.bak"
